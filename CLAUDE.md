# Project Instructions — Video Conferencing App

Read this before doing any work in this repo. Full detail lives in the docs below — this file is the standing summary Claude should always follow without being reminded.

## Reference docs (source of truth — don't re-decide what's already decided here)

- [TECH_STACK.md](./TECH_STACK.md) — frozen stack: Next.js/React Native frontend, NestJS backend, LiveKit (Go) for media, Postgres + Redis, Clerk/Auth0 auth
- [WEBRTC_LIVEKIT.md](./WEBRTC_LIVEKIT.md) — LiveKit deployment, tokens/grants, codecs, recording, TURN
- [FEATURES.md](./FEATURES.md) — scoped feature tiers v1 (MVP) → v4 (AI-driven), plus a Tier 5 deferred backlog for items that need their own dedicated design/decision time (SSO, recurring meetings, recording, real calendar sync, notifications, mobile). Build strictly in tier order.
- [DEV_STANDARDS.md](./DEV_STANDARDS.md) — design principles, patterns, naming, API versioning, security checklist, packages

## Non-negotiable rules

1. **Don't re-litigate the stack.** If asked "should we use X instead," check `TECH_STACK.md` first — only revisit if the user explicitly asks to reconsider a specific decision.
2. **Security is not optional, especially:**
   - Every endpoint that fetches a resource by ID must verify ownership/access **at the database query level**, not just via a route guard (Broken Object Level Authorization is the single most common real API vulnerability — see `DEV_STANDARDS.md` §6).
   - Every request body/query needs a DTO with `class-validator`, `whitelist: true`. Never read raw `req.body` unvalidated.
   - Never hardcode secrets, API keys, or tokens. Never log tokens or credentials.
   - Never disable DTO validation, Helmet, or CORS restrictions to "get something working quickly."
3. **Follow the folder structure in `DEV_STANDARDS.md` §3.1:**
   - NestJS: feature-based modules (controller + service + DTOs + tests together per feature)
   - Next.js: `app/` is routing only — business logic goes in `features/<domain>/`, never in route files
4. **Naming:** kebab-case files, PascalCase classes/components, camelCase variables, plural-noun REST routes. See `DEV_STANDARDS.md` §4.
5. **Design principles:** SOLID, constructor-based DI, Guards for auth (never scattered role checks), Repository pattern (never call Prisma directly from a controller). Don't build abstractions for a hypothetical second use case — three similar lines beat a premature abstraction.
6. **Build in tier order.** Do not implement Tier 2/3/4 features (`FEATURES.md`) while Tier 1 is incomplete.
7. **Before marking any feature done:**
   - Run lint + type-check + tests
   - Use the `verify` skill to actually run the app and confirm behavior — passing tests isn't the same as a working feature
   - For UI changes, use `run` or the browser tools to visually confirm before reporting done
8. **Before merging any non-trivial change**, invoke the `production-readiness-guardian` subagent (`.claude/agents/production-readiness-guardian.md`) to check security, patterns, folder placement, simplicity, and production-readiness.

## Workflow shortcuts

- `/code-review` before merging a feature branch (`ultra` for major releases)
- `security-review` on any auth, payment, or LiveKit token/signaling code
- `/simplify` after a feature works, before merge
- `production-readiness-guardian` agent for the full standards check (see above)

## Current phase

Monorepo scaffolded (`apps/web`, `apps/backend`, `packages/shared`, Turborepo + pnpm). Backend has: custom auth (argon2, rotating refresh tokens), Room/Meeting CRUD with per-resource authorization guards, LiveKit token issuance wired into the join flow, host-only admin actions (mute participant audio, remove participant) backed by `RoomServiceClient`, and a host-admit waiting room (`Participant.admittedAt` — null until the host admits; a LiveKit token is only ever issued once it's set). Auth is **custom-built**, not Clerk/Auth0 (reversed from the original `TECH_STACK.md` plan — see §5 there for why). LiveKit is **self-hosted locally** via `infra/livekit/docker-compose.yml` (`--dev` mode), not Cloud.

Frontend has a working call UI (`CallRoom` wrapping `@livekit/components-react`'s `VideoConference` prefab), a `HostControls` panel for muting/removing participants mid-call, and a `WaitingRoomHostPanel` for admitting/denying joiners — both host-only, both rendered together in `CallRoom` (disambiguated in tests via `data-testid`). A non-host joiner sees `WaitingRoom`, which polls `GET /rooms/:id/join-status` every 2s until the host acts. Covered end-to-end by Playwright: `two-user-call.spec.ts`, `waiting-room.spec.ts`, and `join-by-code.spec.ts`. `playwright.config.ts` runs with `workers: 1` — multiple spec files registering real accounts in parallel workers trips the backend's own `/auth/register` throttle; even serialized, a full run across all spec files needs ~60s between attempts to stay under the register/login throttle budgets.

Scheduled meetings and join-by-code are both done: `CreateRoomForm` has a "Schedule for later" toggle (backend rejects a past `scheduledFor`, checked at the service layer not just client-side); scheduled meetings show "Add to Google Calendar" / "Add to Outlook" / "Download .ics" links (`calendarLinks.ts` — pure client-side URL/`.ics` generation, no OAuth, no stored tokens; see FEATURES.md's Research notes for why the full calendar-API-sync version is separately scoped and much bigger). Every room also gets a `joinCode` (9 random digits, e.g. "482 913 657") generated at creation and resolved via `GET /rooms/by-code/:code`, throttled tighter than the global default (15/min) since a 9-digit code is a much smaller keyspace (~30 bits) than the UUID room IDs (122 bits) and is otherwise a realistic brute-force/enumeration target. Reminder emails are deliberately NOT built yet — decided to skip email infrastructure until a provider is chosen (Postal self-hosted needs a domain + DNS control the project doesn't have configured yet; Resend/SES flagged as the faster managed alternative) rather than build against a stub.

**To run locally:** Postgres running with `DATABASE_URL` in `apps/backend/.env`; `docker compose -f infra/livekit/docker-compose.yml up -d` for LiveKit; `pnpm --filter backend run start:dev`; `pnpm --filter web run dev`. E2E: `pnpm --filter web exec playwright test` (needs backend + LiveKit + Postgres running; leave ~60s between runs — `/auth/register` and `/auth/refresh` are both throttled and the suite runs close to those limits).

**Tier 1 is complete** — the remaining originally-v1 items (recording/Egress, recurring meetings, real calendar OAuth sync, email/push notifications & reminders, SSO, mobile) each needed their own dedicated design/decision time rather than being a natural extension of existing code, so they've been moved to FEATURES.md's **Tier 5 — Deferred** section.

**Tier 2 has started:** virtual backgrounds + background blur are done, via LiveKit's own `@livekit/track-processors` package (MediaPipe selfie-segmentation, entirely client-side — no backend involvement, since it's a per-participant local video effect). `BackgroundEffectsControl` renders for every participant (not host-gated, unlike `HostControls`), dynamic-imported with `ssr:false` in `CallRoom` since the package pulls in a large WASM bundle and touches browser-only APIs at import time. The segmentation model loads from a CDN at runtime (`@mediapipe/tasks-vision`'s WASM/model files) — a real, user-visible failure mode (blocked network, corporate proxy) that's now wrapped in try/catch with a visible error message, and an unsupported browser shows an explanation rather than the control just vanishing.

Noise cancellation is also done — but deliberately **not** via LiveKit's own `@livekit/krisp-noise-filter`: researched it first and confirmed (LiveKit's docs + a GitHub issue closed "not planned" by their maintainers) that Krisp is locked to LiveKit Cloud accounts, which doesn't work for this project's self-hosted setup. Used RNNoise instead (`@sapphi-red/web-noise-suppressor`, genuinely open-source) via a custom `NoiseCancellationProcessor` modeled directly on `@livekit/track-processors`' own `GainAudioProcessor` reference implementation. Its AudioWorklet script + WASM binaries are copied from `node_modules` into `apps/web/public/rnnoise/` at install time (`scripts/copy-rnnoise-assets.mjs`, wired to `postinstall`) since Next.js has no Vite-style `?url` import for this — the copied output is gitignored, not committed. See FEATURES.md's Research notes for the full Krisp-vs-RNNoise writeup.

Reactions/emojis are also done, via LiveKit's own data channel (`useDataChannel`, topic `"reactions"`) — chosen after an explicit alternatives comparison against a new NestJS WebSocket gateway, third-party realtime SaaS, and a self-hosted broker (see FEATURES.md's Research notes for the full comparison table). **Standing rule going forward, not just for this feature**: before defaulting to a platform's own built-in mechanism, compare real alternatives on two criteria — new security surface, and genuine open-source licensing (a commercial SaaS free tier doesn't count). Verified with a real cross-participant Playwright test (`reactions.spec.ts`) rather than manual browser checking, since this feature is specifically about whether the OTHER person's browser receives the broadcast — exactly what isolated browser contexts are good at proving and a single manual session can't.

Raise hand is also done, via LiveKit **participant metadata**, not the data channel reactions used — the two solve different problems (metadata is resynced by LiveKit to a participant who joins later; a data-channel broadcast is fire-and-forget and would silently miss late joiners entirely). `RaiseHandControl` renders for every participant (not host-gated) and calls `localParticipant.setMetadata()` directly, client-side, for a participant raising/lowering their OWN hand — safe because the LiveKit access token's `canUpdateOwnMetadata` grant (new, added to `createAccessToken`'s `VideoGrant`) is enforced server-side by LiveKit to only ever touch the caller's own metadata, so there's no backend round trip and no way to forge someone else's state. A host lowering ANOTHER participant's hand is a real backend endpoint instead (`POST /rooms/:id/participants/:userId/lower-hand`, `RoomsService.lowerParticipantHand`), guarded by the same `RoomHostGuard` + `assertActiveNonSelfParticipant` DB-level check as mute/remove. No new DB field — raised-hand state lives entirely in LiveKit, not Postgres, since it's live call state with no need for history (see FEATURES.md's Research notes for the fuller metadata-vs-data-channel writeup). Verified with `raise-hand.spec.ts`, which specifically covers a participant joining AFTER a hand is already raised — the scenario that would have caught a wrong (data-channel) transport choice.

Meeting lock is also done: a host-only toggle (`Room.locked`, `POST /rooms/:id/lock` and `/unlock`, `RoomHostGuard`) that blocks brand-new joiners in `RoomsService.joinRoom` without ever affecting someone who already has a `Participant` row for that room — including the host, who is exempt for free since their own row always exists from `createRoom`. The lock check in `joinRoom` deliberately reuses the exact same "existing member" lookup the capacity gate already computes, rather than adding separate logic, so the two checks can't disagree about who counts as a new joiner (see FEATURES.md's Research notes). Rejection is `ForbiddenException('This meeting is locked')`, matching the existing "This meeting is full" style rather than a generic 404. `MeetingLockControl` is a host-only floating toggle in `CallRoom`, following the same panel pattern as `HostControls`/`WaitingRoomHostPanel`. Verified with `meeting-lock.spec.ts`, which specifically covers an already-admitted participant reconnecting while locked (not just a new guest being rejected) since that's the nuance most likely to get broken by a careless implementation.

End-to-end encryption is also done, via LiveKit's own `ExternalE2EEKeyProvider` (Web Worker + Insertable Streams, confirmed via the SDK's actual shipped types — also marked `@experimental` there, worth knowing). LiveKit doesn't solve key distribution, only encryption once you have a key, so the real design work was there: the key is generated client-side and shared only via the room URL's **fragment** (`#key=...`), which no browser ever sends to a server — the only way this is genuinely end-to-end rather than backend-visible. `Room.e2eeEnabled` holds no key material; it only lets `joinRoom` tell a client "this room needs a key you don't have." Consequences worth remembering: join-by-code can't carry a key (refused with a clear message), it's creation-time-only with no live mid-call toggle, scheduled meetings don't get the option yet (no surviving moment to recover the key from afterward), and recording will need to explicitly refuse E2EE rooms once built. See FEATURES.md's Research notes for the full writeup and `e2ee.spec.ts` for what's actually verified (critically: the key never appears in any backend request).

Co-host / multiple hosts is also done: a new `RoomRole.cohost` value on the existing `Participant.role` column (not LiveKit metadata — role gates backend authorization, so it has to be DB-verifiable), promoted/revoked exclusively by the true owner (`POST /rooms/:id/participants/:userId/promote|demote`, `RoomHostGuard`, never `RoomHostOrCoHostGuard`). Call-control and queue-management actions (mute, remove, admit, deny, lock, unlock, lower-hand) extend to a co-host via a new, separate `RoomHostOrCoHostGuard`, deliberately kept apart from `RoomHostGuard` (still strict `Room.hostId`-only for `update`/`cancel`/`end`/promote/demote) so the two privilege levels can't drift together. `CoHostControl` is a host-only panel (`CallRoom`) for managing who's a co-host; `HostControls`/`WaitingRoomHostPanel`/`MeetingLockControl`/`RaiseHandControl` now gate on `canManage` (host or co-host) instead of strict `isHost`. Because a promotion has to visibly unlock those panels for an **already-connected** participant, `CallRoom` polls the existing `GET /rooms/:id/join-status` endpoint every 5s while connected. Verified live end-to-end: a promoted co-host gains host panels mid-call with no refresh, can genuinely mute/lock like a host, and is refused (403) promoting a third participant, demoting the real host, ending the room, or renaming it — confirmed against the real backend, not just hidden UI. See FEATURES.md's Research notes for the full two-guard reasoning.

Picture-in-picture is also done — pure client-side, no backend involvement, the browser's native `HTMLVideoElement.requestPictureInPicture()`. `VideoConference` doesn't expose a ref or hook for "the currently focused video element" (checked its actual shipped source, not just the `.d.ts`, the same way the grid/speaker/gallery rows above were confirmed already-free), so `PictureInPictureControl` falls back to a DOM query scoped by the SDK's own markup — `video.lk-participant-media-video` inside the `LiveKitRoom`'s `[data-lk-theme]` root, a stable class owned by `components-core`'s `setupMediaTrack()`, not a blind `querySelectorAll("video")`. Among the video elements found it prefers a remote participant's over the local camera preview, and among ties picks whichever tile is currently rendered largest, tracking whatever layout is active without duplicating that logic. Gated on real feature detection (`document.pictureInPictureEnabled`), with an explanatory message rather than a silently vanished control when it's false, same pattern as the two effects controls; renders for every participant, not host-gated, since it's a personal viewing preference. See FEATURES.md's Research notes for the full writeup, and `picture-in-picture.spec.ts` for what a Playwright test against a real Chromium can and can't prove about this specific browser API (button visibility and a real, non-crashing `requestPictureInPicture()` call are covered; the resulting OS-level floating window is outside the page's DOM entirely and was confirmed by hand instead).

Polls & Q&A is also done: unlike a reaction or raised hand, a poll's question/options/votes are genuinely persisted (`Poll`/`PollOption`/`PollVote` in `schema.prisma`, one open poll per room at a time), so the design problem was different from raise-hand's metadata fix — a poll's shape (variable option count, a running tally that must be exactly correct) doesn't fit LiveKit metadata, and results must survive a refresh. `PollControl` fetches `GET /rooms/:id/polls/current` via REST on mount for every participant — this, not the LiveKit data channel, is what a late joiner actually sees the poll from, whether they missed the "created" broadcast, missed every vote, or joined after the poll was already closed (`getCurrentPoll` deliberately returns the room's most recent poll whether open OR closed). The data channel (topic `"polls"`) is kept only as a "something changed, refetch" ping, never as the vote data itself, so a dropped broadcast degrades to a late update, never a wrong one. Host-only create/close reuse the existing `RoomHostGuard`; vote/current reuse `RoomMemberGuard` (now exported from `RoomsModule` for this); double-voting is blocked at the database level with `@@unique([pollId, userId])`, not just an application-code check. Verified with `polls.spec.ts`, whose two late-joiner tests connect a fresh participant only after a poll exists (with votes already cast) and again only after it's closed — the scenario a data-channel-only implementation would pass in casual testing and then silently fail in production. See FEATURES.md's Research notes for the fuller writeup.

Meeting analytics is also done: a host-only, read-only view (`GET /rooms/:id/analytics`, `RoomsService.getMeetingAnalytics`) that aggregates the `Participant` rows already recorded by `joinRoom`/`leaveRoom`/`endRoom` — no new table, no LiveKit call. Deliberately available for a room in any status, not just after it ends: duration for anyone still connected (`leftAt: null`) is computed against `now` rather than gating the whole endpoint on `RoomStatus.ended`, since a host asking "who's here right now" mid-call is as real a use case as reviewing a past meeting. A scheduled room nobody has joined yet returns an explicit empty shape instead of computing something misleading from the host's own pre-join `Participant` row. `Room.updatedAt` is deliberately NOT used as "ended at" (it's bumped by unrelated mutations that can happen after a room ends); the meeting's end time is derived instead from the latest `leftAt` among participants, which `endRoom` already sets transactionally when it marks the room ended — see FEATURES.md's Research notes for the full reasoning, including why this is the one method in `RoomsService` that re-verifies the host at the DB level itself rather than trusting `RoomHostGuard` alone (its response is a full participant name + join/leave history dump, the most sensitive read in the Rooms module). Frontend is a separate page (`/rooms/[id]/analytics`, reachable via an "Analytics" link on the room list for rooms the current user hosts), not a live in-call panel, matching the feature's own "attendance, duration, join/leave times" framing as post-hoc-reviewable data. Verified with `meeting-analytics.spec.ts`: a real two-participant call where the guest is genuinely removed mid-call, then the host's analytics page is checked against the real outcome (2 unique participants, one "still in call," one with a real left timestamp and duration), plus a non-host being refused when navigating straight to the URL. Only the single-room view was built; a cross-meeting dashboard was a documented stretch goal, not attempted.

Collaborative whiteboard is also done: a shared, persisted drawing surface (`WhiteboardStroke` rows in Postgres, one per pen-down-to-pen-up gesture) rendered with a plain hand-rolled HTML5 `<canvas>` — no drawing library (`perfect-freehand`/`tldraw`) added, since neither earns its dependency for "a blank canvas with a pen tool" (see FEATURES.md's Research notes for the full alternatives comparison). Everyone can draw (`RoomMemberGuard` on the stroke endpoints), matching this feature's collaborative-by-default scope; only "Clear canvas" is host-only (`RoomHostGuard`), since it wipes out every other participant's work too. New strokes sync live to already-connected participants over LiveKit's data channel (topic `"whiteboard"`, sent reliably — unlike reactions' lossy sends, a dropped stroke would leave two canvases silently disagreeing with no later re-sync). The design point worth remembering: a data-channel broadcast alone would silently fail a participant who joins the call AFTER strokes already exist — the same late-joiner gap raise-hand's Research notes already worked through for participant metadata — so `WhiteboardControl` also fetches the full stroke history via `GET /rooms/:id/whiteboard/strokes` unconditionally on mount, independent of the live channel. Verified with `e2e/whiteboard.spec.ts`, whose core test admits a second guest only after a stroke has already been drawn and broadcast, then checks the canvas's own pixel data (not React state) to confirm that guest actually sees it.

Breakout rooms are also done: a new, deliberately minimal `BreakoutRoom` model (`id`, `label`, `createdAt`, `endedAt`, `roomId`) plus a nullable `Participant.breakoutRoomId` — not a self-referencing `Room`, since almost none of `Room`'s fields (`joinCode`, `scheduledFor`, `locked`, `status`) actually apply to a breakout and reusing it would mean guarding every existing Room-scoped route against ever treating one as a real meeting (see FEATURES.md's Research notes). There is no independent join code or lookup route for a breakout — the only way to ever get a breakout's LiveKit token is `GET /rooms/:id/breakout-rooms/my-assignment`, scoped to the caller's own `Participant` row, so there's nothing for a stranger (or another participant) to wander into. Each breakout is a genuine separate LiveKit room (`RoomServiceClient.createRoom()`/`deleteRoom()` in `LiveKitService`, pre-created host-side via `BreakoutRoomsService.createBreakoutRooms`), with its own scoped access token minted through the same `LiveKitService.createAccessToken` role-based grant logic as the main room. All host actions (create, list, end) go through `BreakoutRoomsController` guarded by the existing `RoomHostGuard` (reused as-is, exported from `RoomsModule`), never a new authorization path. An already-connected participant learns about a new assignment, or that breakouts ended, via `BreakoutRoomAwareCallRoom` polling `GET /rooms/:id/breakout-rooms/my-assignment` every 3s and swapping between two fully separate `LiveKitRoom` connections (remounted via a fresh `key`) — fire-and-forget was rejected because a missed signal would strand a participant with no way to ever get their breakout token, not just a cosmetic miss. A real bug only live multi-room testing caught (not the mocked unit tests): `CallRoom`'s default `onDisconnected` unconditionally exited to `/rooms`, which raced ahead of the 3s poll the instant the host ended breakouts (LiveKit force-disconnects everyone from the deleted room immediately) — fixed with an overridable `onDisconnected` prop that checks `DisconnectReason.ROOM_DELETED` and reconnects to the main room instead of leaving. Scoped out of v1: automatic/random participant distribution (manual assignment only), the host moving between rooms mid-session (host stays in the main room throughout), and E2EE meetings (`createBreakoutRooms` refuses outright rather than silently downgrading security — a breakout has no key-distribution story of its own). Verified with `breakout-rooms.spec.ts` against a real LiveKit server: two guests split into two breakout rooms are confirmed, via `RoomServiceClient.listParticipants` directly against LiveKit (not just the UI), to be in genuinely separate rooms and gone from the main room, and ending breakouts brings all three back together with no action from the guests themselves.

**All of Tier 2 is now done.** Tier 3 has started: meeting templates & agendas is done — a reusable, user-owned `MeetingTemplate` preset (name + default E2EE + a starter agenda) that prefills `CreateRoomForm` (its `templateId` seeds fresh `AgendaItem` rows transactionally at room creation), plus a live, per-room `AgendaItem` checklist (`AgendaControl` in `CallRoom`) that host/co-host manage and every participant can view. `MeetingTemplate` is deliberately NOT room-scoped (no relation to any `Room`, unlike every other feature so far) — ownership is a plain `hostId` check in `TemplatesService`, not a new guard class. Agenda's CRUD lives directly in `RoomsController`/`RoomsService` (mirroring Whiteboard/Meeting-analytics, not a new module), guarded by `RoomHostOrCoHostGuard` for mutations and `RoomMemberGuard` for reads, with the same REST-fetch-on-mount late-joiner pattern Polls/Whiteboard already established. A real bug only live Playwright testing caught: the agenda checkbox's `handleToggle` called `setPending(true)` before updating local state, causing a visible checked→unchecked→checked flicker on every toggle — fixed with an optimistic update in the same tick. See FEATURES.md's Research notes for the fuller writeup and `meeting-templates.spec.ts` for the late-joiner verification. **Not yet built (Tier 5, deferred):** recording/Egress, recurring meetings, real calendar OAuth sync (Google Calendar API / Microsoft Graph — see FEATURES.md), email/push notifications & reminders (blocked on an email provider decision), SSO, mobile. Also not yet built: screen-share-specific controls beyond the SDK default. Flagged but not actioned: cross-tab/cross-app annotation (Tier 3 — see FEATURES.md Research notes for why that variant isn't a web-app feature at all, unlike the in-app whiteboard above).

Git workflow in use: feature branches off `dev` (e.g. `feature/auth`, `feature/rooms`, `feature/livekit`), merged back into `dev`, pushed to `origin`. `master`/`main` is never touched or pushed.
